## About

`openfiat-specs` is part of the [OpenFiat](https://github.com/OpenFiat-org)
ecosystem — an open, decentralized peer-to-peer protocol for exchanging
stablecoins for local fiat currency. Solana secures asset settlement through
audited smart contracts; OpenFiat coordinates the peer-to-peer marketplace
layer (discovery, advertisements, reputation, governance, notifications, and
more) without centralized infrastructure.

For the full protocol motivation and design, see the
[whitepaper](https://github.com/OpenFiat-org/openfiat-specs) and the
[protocol specifications](https://github.com/OpenFiat-org/openfiat-specs/tree/main/Whitepaper/Specifications).

## Repository layout

```text
.
├── Whitepaper/
│   ├── Chapters/         # 00 - Preface .. 27 - Conclusion (canonical prose spec)
│   ├── PDF/               # rendered PDF of every chapter, numbered to match Chapters/
│   ├── Specifications/     # OFS-#### protocol specs (OFNP, OFTP, OGP, ORE, ...)
│   └── Archive/           # superseded drafts, kept for historical reference
├── docs/                  # meta-documentation about this repo (not the protocol itself)
└── examples/
```

**The `Whitepaper/` directory is the canonical source of truth and is not
regenerated by tooling in this repository.** Changes to it go through the RFC
process (see [CONTRIBUTING.md](CONTRIBUTING.md)) rather than direct edits.

## Quick start

Browse the whitepaper starting from
[`Whitepaper/Chapters/00 - Preface.md`](Whitepaper/Chapters/00%20-%20Preface.md),
or jump straight to the machine-readable protocol specifications in
[`Whitepaper/Specifications/`](Whitepaper/Specifications/) (each document is
identified by an `OFS-####` number, e.g. `OFS-1000` is the Network Protocol).

Rendered PDFs of every chapter are available under
[`Whitepaper/PDF/`](Whitepaper/PDF/) for offline reading and distribution.

## Development

This repository has no build step — it is documentation. If you are
proposing a change:

1. Open an RFC issue describing the proposed change to the specification.
2. Once there is rough consensus, submit a PR editing the relevant chapter(s)
   in `Whitepaper/Chapters/` and/or spec(s) in `Whitepaper/Specifications/`.
3. Do not renumber or rename existing chapters/specs in the same PR as a
   content change — renumbering is a separate, low-risk mechanical PR.
4. PDF regeneration (`Whitepaper/PDF/`) happens as part of the release
   process, not on every commit.
5. Commit messages follow Conventional Commits — enforced by `commitlint`
   on `commit-msg` (see `commitlint.config.js`).

Install the local hooks once with `pre-commit install --hook-type
pre-commit --hook-type commit-msg` (`.pre-commit-config.yaml`): trailing
whitespace, EOF newlines, YAML/TOML/JSON validity, `editorconfig-checker`,
and the same `markdownlint-cli2` rules CI runs, so a failing check surfaces
before you push rather than in CI.

## Testing

CI (`.github/workflows/ci.yml`, job `markdownlint / yamllint`) runs
`markdownlint-cli2` against every Markdown file and `yamllint` against every
YAML file on each push and PR to `main`. There is no link-validity check and
no runtime test suite — this is a documentation repository.
